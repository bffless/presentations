Context, RAG & Vector Search

How AI assistants find what they don't know

BFFless · rag.bffless.dev

Arc of the talk: what an assistant actually "knows" (its context), how RAG lets it look things up (the library), how that lookup works under the hood (vectors ≈ lat/long), and a real implementation: BFFless Recall.
Part 1

What is Claude / ChatGPT,
and what does it actually know?

A model is a frozen snapshot

  • Trained once, on a huge snapshot of text. Then frozen.
  • At runtime it does one thing: predict the next word from what's in front of it
  • It has no memory of you, your company, or anything after training day
Demystify: it's not a database and not "looking things up" by default. Everything it appears to know was baked in at training time.

The context window

Context = everything the model can see right now

  • Your messages, instructions, files, tool results: all of it
  • It's a finite budget (hundreds of pages, not a hard drive)
  • If it's not in the context, the model doesn't know it. Full stop.
This is the single most important concept of the talk. Everything else — RAG, vectors, Recall — exists to answer "how do we get the right stuff into this window?"

A coding agent starts somewhere

The agent bootstraps context from the filesystem: project instructions first (CLAUDE.md / AGENTS.md), then skills when a task matches, then whatever it reads while working. Context accretes — it starts nearly empty and fills as the session goes. The dashed space matters: the window is finite, which is the next slide.

The problem

You can't stuff everything in. What if the model could go look things up?

Three pressures: the knowledge is huge, the window is small and costly per token, and the knowledge keeps changing while the model's training data stands still.
Part 2

RAG — give the model a library card

Retrieval-Augmented Generation

  • Don't teach the model everything up front
  • At question time: retrieve the few most relevant passages, put them into context
  • The model answers grounded in what it just read

The library analogy

I don't know everything in the library. I know how to search it.

Key point: expertise-on-demand beats memorizing the collection. The librarian doesn't memorize books either — they're expert at *finding*. RAG makes the model a great library patron: walk in with a question, search the catalog, pull one book, read the relevant chapter.

The RAG loop

Walk the numbers: (1) the question goes to a retriever, not straight to the model; (2) the retriever searches the knowledge store, which lives outside the model and can be updated any time; (3) only the top matches join the question in the context, so it stays small; (4) the model answers grounded in what it just read and can cite it.
Part 3

Under the hood — searching by meaning

Keyword search isn't enough

  • Keywords find words, not meaning
  • "car" misses "automobile"; "how do I deploy" misses "shipping to production"
  • The library catalog needs to understand what a book is about

"Restaurants near me"

Everyone has used vector search already: Google Maps. Every restaurant is a point, (lat, lng), just two numbers; "near me" is nearest-neighbor math on those points. Hold onto this picture — the next slide is the same picture.

Embeddings: lat/long for concepts

Deliberately the same picture as the map: an embedding model assigns every piece of text coordinates, and the axes are meaning instead of geography. Related concepts cluster the way nearby restaurants cluster, so "how do I deploy?" lands next to "shipping to production" even though they share no words. Don't over-explain the 1,024 dimensions; "coordinates for meaning" is the point.

Vector search = the catalog is a map

  1. Ahead of time: embed every chunk of every document, store the vectors
  2. At question time: embed the question with the same model
  3. Find the nearest stored vectors — those chunks are your answer material

"Nearest" = cosine similarity, the same math family as distance-on-the-map.

Part 4

How BFFless does it: Recall

Video transcript RAG — upload → transcribe → publish → ask

Recall in one slide

  • Admin uploads videos; transcripts get chunked and embedded
  • A public site searches and chats over them
  • Answers deep-link to the exact second of the video
  • No app server — everything is BFFless pipelines

Ingest: three staged steps

A draft video has zero vectors, so search structurally cannot surface it. No "hide from search" flag to forget.

Step 1: presigned upload straight to the bucket. Step 2: WhisperX runs in the pipeline's background steps and writes a transcript with per-word timestamps. Step 3 is the design decision worth dwelling on: publish IS indexing — chunk, embed via Replicate, store in pgvector. Unpublish deletes the vectors. Content that isn't published has no coordinates, so the search space simply doesn't contain it.

Chunking the transcript

45-second windows, capped at 120 words. The chunk text is pure transcript; timing rides in metadata.

The chunk *text* is pure transcript words; timing rides in metadata that comes back with every search hit. That separation is why answers can cite an exact second. The word cap (120) closes a window early on dense speech, with a matching word-overlap cap so overlap never explodes.

Building the vectors

  • Each chunk goes to Replicate, running the bge-large-en-v1.5 embedding model
  • Back comes a 1,024-dimensional vector per chunk
  • Stored in CE's Postgres with pgvector: the database is the vector DB
Replicate hosts the embedding model so CE doesn't need a GPU. pgvector means no separate vector database to run — vectors live next to the rest of the data. (We'll dive into the actual table/handler details in the collaborative pass — embed_store handler, vector column, etc.)

Asking a question

One embedding space for search and chat. Change the embedding model and every video must be re-indexed.

The question takes the same path the chunks took: embedded with the same pinned model, so question and chunks live in one space. vector_search returns the nearest chunks with their timing metadata; the search page shows them raw, and chat is classic RAG — Claude gets the chunks as a tool result and cites the exact second.

Recap

  • A model only knows what's in its context
  • RAG: search the library, don't memorize it
  • Vector search: lat/long for meaning
  • Recall: transcripts → pgvector → second-exact answers
