Context, RAG & Vector Search

How AI assistants find what they don't know

BFFless · rag.bffless.dev

Arc of the talk: what an assistant actually "knows" (its context), how RAG lets it look things up (the library), how that lookup works under the hood (vectors ≈ lat/long), and a real implementation: BFFless Recall.
Part 1

What is Claude / ChatGPT,
and what does it actually know?

A model is a frozen snapshot

  • Trained once, on a huge snapshot of text. Then frozen.
  • At runtime it does one thing: predict the next word from what's in front of it
  • It has no memory of you, your company, or anything after training day
Demystify: it's not a database and not "looking things up" by default. Everything it appears to know was baked in at training time.

The context window

Context = everything the model can see right now

  • Your messages, instructions, files, tool results: all of it
  • It's a finite budget (hundreds of pages, not a hard drive)
  • If it's not in the context, the model doesn't know it. Full stop.
This is the single most important concept of the talk. Everything else — RAG, vectors, Recall — exists to answer "how do we get the right stuff into this window?"

A coding agent starts somewhere


$ cd my-project
$ claude

You launch it in a folder, and that folder is its world

Context builds in layers:

  • CLAUDE.md / AGENTS.md — standing instructions
  • Skills — task know-how loaded on demand
  • Files it reads as it works
  • The conversation itself
The agent bootstraps context from the filesystem: project instructions first, then skills when a task matches, then whatever it reads while working. Context accretes — it starts nearly empty and fills as the session goes.

The problem

  • Your knowledge is huge: docs, wikis, tickets, code history, videos…
  • The context window is small and every token costs time and money
  • And your knowledge changes; the model's training data doesn't

You can't stuff everything in.
What if the model could go look things up?

Part 2

RAG — give the model a library card

Retrieval-Augmented Generation

  • Don't teach the model everything up front
  • At question time: retrieve the few most relevant passages, put them into context
  • The model answers grounded in what it just read

The library analogy

I don't know everything in the library.
I know how to search it.

  • Walk in with a question
  • Search the catalog → pull one book off the shelf
  • Read the relevant chapter → expert on that one topic, right now
  • Never need to know what the other million books say
Key point: expertise-on-demand beats memorizing the collection. The librarian doesn't memorize books either — they're expert at *finding*. RAG makes the model a great library patron.

The RAG loop

question → retrieve top matches → add them to the context → model answers (with citations)

  • Knowledge lives outside the model — update it any time
  • Answers can cite their sources
  • Context stays small: only what this question needs

Part 3

Under the hood — searching by meaning

Keyword search isn't enough

  • Keywords find words, not meaning
  • "car" misses "automobile"; "how do I deploy" misses "shipping to production"
  • The library catalog needs to understand what a book is about

"Restaurants near me"

  • Every restaurant is a point: (lat, lng), just two numbers
  • "Near me" = smallest distance between points
  • A 2-dimensional vector locates anything on Earth
Everyone has used vector search already — Google Maps. Two numbers place a point; nearest-neighbor math finds the closest ones. Hold onto that picture. (Diagram placeholder: simple 2D map scatter with "you are here" + nearest points.)

Embeddings: lat/long for concepts

  • An embedding model maps text → a point in ~1,000-dimensional space
  • Similar meaning → nearby points
  • "car" and "automobile" land close together; "banana" lands far away

Same trick as the map — just more dimensions, and the axes are meaning, not geography.

Don't over-explain the dimensions — the point is "coordinates for meaning". Related concepts cluster the way nearby restaurants cluster.

Vector search = the catalog is a map

  1. Ahead of time: embed every chunk of every document, store the vectors
  2. At question time: embed the question with the same model
  3. Find the nearest stored vectors — those chunks are your answer material

"Nearest" = cosine similarity, the same math family as distance-on-the-map.

Part 4

How BFFless does it: Recall

Video transcript RAG — upload → transcribe → publish → ask

Recall in one slide

  • Admin uploads videos; transcripts get chunked and embedded
  • A public site searches and chats over them
  • Answers deep-link to the exact second of the video
  • No app server — everything is BFFless pipelines

Ingest: three staged steps

  1. Upload — video/audio goes straight to the bucket
  2. Transcribe — WhisperX writes a transcript with per-word timestamps
  3. Publish = index — chunk → embed → store; the only way content enters the search space
The publish gate is a design decision worth dwelling on: a draft video has *zero* embeddings, so search structurally cannot surface it. No "hide from search" flag to forget.

Chunking the transcript

  • Windows target 45 seconds, capped at 120 words
  • Overlapping windows so no thought gets cut at a boundary
  • Each chunk keeps {start, end} metadata: that's what powers second-exact deep links
The chunk *text* is pure transcript words; timing rides in metadata that comes back with every search hit. This separation is why answers can cite an exact second.

Building the vectors

  • Each chunk goes to Replicate, running the bge-large-en-v1.5 embedding model
  • Back comes a 1,024-dimensional vector per chunk
  • Stored in CE's Postgres with pgvector: the database is the vector DB
Replicate hosts the embedding model so CE doesn't need a GPU. pgvector means no separate vector database to run — vectors live next to the rest of the data. (We'll dive into the actual table/handler details in the collaborative pass — embed_store handler, vector column, etc.)

Asking a question

  1. Your question is embedded with the same model
  2. vector_search finds the nearest chunks in pgvector
  3. Search shows them directly; chat hands them to Claude as a tool result — classic RAG

One embedding space for search and chat — change the model, re-index everything.

Recap

  • A model only knows what's in its context
  • RAG: search the library, don't memorize it
  • Vector search: lat/long for meaning
  • Recall: transcripts → pgvector → second-exact answers
