Part 1

What MCP actually is

A model can read, not do

RAG gave the model a library card.
MCP gives it hands.

"Find me a restaurant" is retrieval. "Book the table" is an action — and no amount of context will make a paragraph book anything.

Callback to the RAG talk: everything the model knows is in its context window, and retrieval is how the right things get in there. Actions are a different problem: the model needs something outside itself that it can invoke and get a result back from. That's MCP: a protocol for offering a model a list of things it may do.

Host, client, server

Three words people mix up. The host is the app the person is using; it embeds a client per server it connects to; the server is yours. The important consequence: the host decides what the model sees, so your job is to publish an honest, well-described list of tools and enforce your own rules behind them.

The restaurant

Plant the seed for Part 3. In most MCP servers the menu is written separately from the kitchen: a tool function, a schema, and a backend endpoint, kept in sync by hand. Drift is the normal failure. In BFFless the tool points at a rule that already exists, so the menu is literally derived from the kitchen.

Just JSON-RPC over HTTP


{ "jsonrpc": "2.0", "id": 1, "method": "tools/list" }
            

{ "tools": [ {
  "name": "generate_image",
  "description": "Generate one image with google/nano-banana-2 on Replicate.
                  Costs money per call — ask the person before calling.",
  "inputSchema": {

Streamable HTTP, stateless: one message per POST.

This is the real answer from the images server. Two things to point at: the description is prompt engineering — it is what the model reads when deciding whether to call you — and inputSchema is plain JSON Schema. No sessions, no SSE stream to keep alive; every POST is self-contained.

A tool call, end to end


{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "generate_image",
              "arguments": { "prompt": "a broken heart wired with circuit traces",
                             "aspect_ratio": "16:9" } } }
            

{ "content": [ { "type": "text",

                         "model": "google/nano-banana-2",

The text line is what the model reads. structuredContent is data for the host.

The text line is your last chance to steer the model: ours tells it the URL expires and to save the file now. structuredContent is the machine-readable twin — the host can render it, store it, hand it to code. Both come from the same tool result.

Where it breaks

Writing the tool: an afternoon.
Hosting it so a stranger's client can log in:
the rest of the month.

Everyone's first MCP server runs locally over stdio and works in fifteen minutes. The moment you want it on the internet, connected from claude.ai by someone who is not you, the problem changes shape completely. That's Part 2.
Part 2

The boss level is auth

The usual build

  • An SDK and a process — genuinely easy, genuinely fine for local stdio
  • Somewhere to run it. TLS. A domain. Uptime.
  • And then: who is calling, and are they allowed?

The hello-world is thirty lines. The login story is the rest of the spec.

Don't dunk on the SDKs — they're good, and stdio servers on your own machine are a perfectly happy ending. The cliff is remote + multi-user. That's where the interesting engineering is, and it is all auth.

What claude.ai expects

There is no "paste an API key" field in claude.ai. Your server must be an OAuth protected resource.

Name the four RFCs once and move on — nobody memorises them, they just need to know this is a real spec stack and not something to improvise. The one step that isn't machinery is the consent page: a human, looking at a list of scopes, deciding. Everything else is discovery so the client can find that page on its own.

Three ways in

Credential Who is it Scopes enforced?
session cookie you, signed in to the instance no
X-API-Key you, from a script or CI no
OAuth app token an app acting for you yes

A person acting as themselves isn't a delegation. Only delegations get scope-checked.

This table pre-empts an hour of confusion. Roles always apply — the tool is admin-only whichever credential arrives. Scopes only exist to bound what you handed to a third party, so a cookie or your own API key sails past them. That's also the one-line path for your own use: an API key in a header, no OAuth at all.

And the good news

Every BFFless instance already runs
that authorization server
on its admin host.

The consent page, dynamic client registration, PKCE, token issue and revoke — CE ships all of it. Which means the part of the deep dive that would normally be a month of work is a field in a JSON document. That's Part 3.
Part 3

The rule set is the server

An endpoint, a tool, a discovery document

Three rules

The whole architecture. Coral is the thing we're building, teal is the auth machinery, violet is the client. Nothing here is a process you deploy — all three boxes on the left and bottom are proxy rules in one rule set. Push the set and the server changes.

Rule 1 — the endpoint


methods: [GET, POST, DELETE]
targetUrl: pipeline
pipeline:
  name: images MCP endpoint
  steps:
    - id: mcp
      handler: mcp_handler
      config:
        serverInfo: { name: bffless-presentations-images, version: 0.1.0 }
        instructions: "One tool, generate_image: …"
        tools: [ … ]
  validators:
    - type: auth_required

GET and DELETE answer 405 — no sessions, no SSE. An empty auth_required is deliberate.

One step. serverInfo and instructions are what the client shows the model about the server as a whole. The validator with no config means: anyone signed in may read the menu, and an anonymous caller gets the 401 that kicks off OAuth discovery. That 401 is a feature, not an error.

Tools are sibling rules


tools:
  - name: generate_image
    description: "Generate one image with google/nano-banana-2. Costs money
                  per call — ask the person before calling."
    inputSchema:
      type: object
      properties:
        prompt:       { type: string }
        aspect_ratio: { type: string, enum: [16:9, 1:1, …] }
      required: [prompt]
    annotations: { readOnlyHint: false, openWorldHint: true }
    rule: { path: /api/mcp-tools/generate, method: POST }

The menu is printed from the kitchen.

The last line is the whole trick. rule.path points at a rule that already exists in this set — a normal pipeline you could curl. On tools/call, CE invokes it in-process as the caller, with the arguments as the body for POST or the query string for GET. No HTTP hop, no second credential, no drift between the menu and what the backend can actually do.

Rule 2 — the tool

The validator on the sibling is the tool's gate: roles and scopes are enforced here, not in the MCP step. Which means a tool is exactly as secure as the endpoint it already was. Notice you can curl this rule directly with an API key and it behaves identically — the MCP step is just another caller.

Shaping the answer

You shape it

Answer a body that already has content[] and it's passed through verbatim — text, structuredContent, isError, all yours.

CE wraps it

Answer plain JSON and CE turns it into a text block plus structuredContent for you.

Failures map cleanly: 401 → auth · 403 → scope · anything else → a pipeline error.

Take the pass-through path whenever the wording matters — the text line is the model's instruction sheet. The wrap is there so an existing JSON endpoint becomes a usable tool with zero changes, which is the fastest way to try this on a backend you already have.

Rule 3 — discovery


pathPattern: /.well-known/oauth-protected-resource*
methods: [GET]
targetUrl: pipeline
pipeline:
  steps:
    - id: discovery
      handler: oauth_protected_resource
      config:
        resource: /api/mcp
            

{ "resource": "https://mcp.bffless.dev/api/mcp",
  "authorization_servers": ["https://admin.bffless.dev"],
  "scopes_supported": ["images:generate"],
  "bearer_methods_supported": ["header"] }
One step, one field. Everything else — the host, the admin authorization server, the scope list — is derived. Before CE 0.4.52 you wrote this document by hand in a function_handler with bypassVisibility; that form still works, and the presentations repo carried it for a while, but the answer is upgrade.

Two steps, one pairing

The pairing is two-way and both forms tell you about it. Discovery looks up the set's mcp_handler rule by the resource path and derives scopes from its tools' siblings; the MCP step's Server tab looks for a discovery rule and reports what it will answer. The third leg is the 401 header pointing at the document — that's how a client that knows nothing finds its way in.

Why it bypasses the gate

The caller has no credential yet.
By definition.

  • The bypass applies only on the well-known path…
  • …and only when the discovery step is the rule's first enabled step

Migrating means deleting the old hand-written step, not adding the new one after it.

This is the failure mode worth showing on screen: leave an old function_handler step enabled ahead of the discovery step and the bypass silently switches off. On a private deployment the document then answers the normal gate, the client never sees it, and you get "connected, but no consent page ever appeared" with nothing in the logs that looks wrong.

Scopes are an allowlist

  • Omitted → the union of every tool's requiredScopes
  • Declared → the only scopes a client may ever ask for
  • A tool whose scope isn't listed can never be called over OAuth

Which is how you keep a CI-only scope out of what claude.ai is even allowed to request.

The one security slide. Derive is the right default — it can't drift. Declare when you deliberately want a narrower surface than the rules imply: the tool still exists, your API key still calls it, but no OAuth client can request the scope it needs, so no consent page can ever grant it.

No secrets in the repo: the Replicate token lives in the project's AI Services settings, and the connection is OAuth. Because the set is the project default, the endpoint rides along on rag.bffless.dev and mcp.bffless.dev alike — which is exactly how the hero image on slide one got made.

Refuse before you spend


// prep.fn.js — the tool rule's first step
function handler({ request }) {
  var body = (request && request.body) || {}
  var prompt = typeof body.prompt === 'string' ? body.prompt.trim() : ''
  var ratio  = body.aspect_ratio || '16:9'

  if (prompt === '') return refuse('prompt is required', '', ratio)
  if (prompt.length > MAX_PROMPT) return refuse('prompt is too long', '', ratio)
  if (RATIOS.indexOf(ratio) === -1) return refuse('aspect_ratio must be one of …')
  // reference images must be https:// …

  return { ok: true, error: '', prompt: prompt, aspectRatio: ratio, images: images }
}

CE does not check tools/call arguments against your inputSchema. The tool does.

That last line surprises people. The schema is advice to the model, not a contract the server enforces — models get it wrong, and a hostile client ignores it entirely. Here a refusal skips the replicate step, because its condition is steps.prep.ok, so a bad call costs nothing.

Talk to the model


// reply.fn.js — Replicate's output becomes a CallToolResult
var text =
  'Image ready (' + prep.aspectRatio + ', ' + MODEL + '). The URL is valid ' +
  'for about an hour: ' + url +
  '\nSave it now, e.g. curl -sL -o decks/<deck>/public/images/<slug>.png "' + url + '"'

return { json: JSON.stringify({
  content: [{ type: 'text', text: text }],
  structuredContent: { url: url, model: MODEL, aspect_ratio: prep.aspectRatio,
                       prompt: prep.prompt },
}) }

The prompt engineering lives in the tool result.

Descriptions steer whether a tool gets called; the result steers what happens next. "The URL expires in an hour, here is the exact command to save it" is the difference between an agent that keeps the image and one that hands you a dead link tomorrow.

Tests without spending


npx bffless rules test .bffless/proxy-rules/images   # fixtures per function
npx bffless rules validate                            # schema + references
npx bffless rules push --dry-run                      # diff against live
  • *.fn.test.yaml fixtures cover every refusal path
  • A GitHub Action syncs the set on push to main

The admin UI is the learning surface; git is the power-user surface.

The functions are pure — arguments in, object out — so the whole validation layer is testable with no network and no spend. Worth stressing: rules push overwrites dashboard edits by design, so pick one source of truth per set and stick to it.

The skill's one rule

  1. Draft the prompt and the aspect ratio
  2. Say plainly this is one paid generation, and wait for a yes
  3. Call generate_image — one image per yes
  4. curl the URL into public/images/ within the hour
  5. Report the saved path and the prompt used

A tool's manners belong in a skill, not in the server.

The server enforces who may spend; the skill decides how politely. That split matters: rules that live in the server apply to everyone forever, and "ask me first" is a preference, not a security boundary. Also: "make it more blue" is a new prompt and a new yes.

Beyond tools

Two surfaces, one shape

Admin UI

A form editor: Server, Tools, Resources, JSON tabs, and a problems panel that tells you the sibling rule doesn't exist yet.

Rules as code

YAML in git, fixtures, dry-run diffs, sync on merge.

rules push overwrites dashboard edits by design. Pick one source of truth per set.

Both surfaces write the same rule. Learn in the UI, where the problems panel catches a mistyped path in a second; move to git when the set matters enough to review. The overwrite is intentional — a set in git is a declaration of what the set should be.

ui:// resources

  • Static documents, or templates with {var} placeholders
  • A listing so the client can browse them
  • A CSP naming what the page may load

Same mcp_handler, plus resources — which is how a BFFless app's own page mounts inside claude.ai. That's its own talk.

Teaser only, ninety seconds. Show the Workflow app's run page rendered inside claude.ai if the recording has it. The point for today: the same rule you just built is the entry point for the interactive surface too — tools were not a special case.

Not the admin MCP server

admin.<host>/mcp drives the admin panel.
Yours lives on your alias.
Different thing.

One slide to pre-empt the most common comment. The admin MCP server lets an agent manage projects, deployments and rules for you. The one you just built is your app's API, on your app's host. They share a protocol and nothing else.

When it doesn't work

SymptomFirst check
no consent page ever appearscurl the discovery doc with no credential
invalid_scopescope missing from scopes_supported
insufficient_scopereconnect and grant it
"declared but no rule answers"path, method, is the set attached?

And a 405 on GET /api/mcp is correct, not a bug.

The unauthenticated curl of the well-known document is the first check every single time — it separates "my server is fine, the client can't find it" from everything else. Nine times in ten it's the visibility bypass or a set that was never attached to the alias.
