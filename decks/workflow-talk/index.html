Part 1

The idea

For everyone: what Workflow is and why it exists.

Every pipeline wanted its own UI

"Studio is really cool — but it's a UI wrapped around one big pipeline. The moment I wanted a version for meetings, or a capture tool, I was looking at building another UI. And another. Every one hand-soldered, every one mine to maintain." The real goal: keep building pipelines, stop building UIs.

Write YAML, get the UI

The pitch. The workflow file on the left is the only thing you write. The harness reads it and renders the run: the graph, live status per step, inputs up front, and — the coral card — steps that pause for a person. "It's an abstraction over the UI layer. Studio as an app, and Studio as a workflow, do the same work."

If you've written a GitHub Action…

on · jobs · steps · matrix · needs — same shape

"The model is very much a GitHub pipeline — that was the inspiration." A workflow has a trigger (on: manual with inputs), jobs that depend on each other with needs, steps inside jobs, and matrix strategies to fan out. If you can read a .github/workflows file you can read these.

Four kinds of step

Where it differs from Actions: every step says uses: one of four things. pipeline — a BFFless proxy rule runs server-side (AI calls, ffmpeg, storage). script — a small TypeScript function the harness runs in a sandbox. island — a real UI the run pauses on, for a human (Studio's cut editor). form — a declared form: fields in, values out. That's the whole vocabulary.

One harness, many workflows

Two repos. The harness is the app — bffless/apps, apps/workflow — deployed once. Implementations are content: bffless/workflow-implementations holds workflow-studio, capture and hello, each published into its own BFFless project. A new workflow is a folder, not a new app. "I can make a Studio geared towards meetings without rebuilding the UI."

Part 2

Inside workflow-studio

For builders. The most complicated implementation — taken apart.

Nine jobs, one file

.bffless/workflows/studio.workflow.yaml

The whole of Studio is one ~540-line file. Double track = matrix (parallel legs): per-video runs once per recording, per-scene once per scene the director picks. Violet = the AI director. Coral = the human trim. After stitch it branches: describe, blog and cover all run off the finished cut.

Fan out, fan in

matrix fans out · max-parallel is the gate · needs fans in

SCREEN (YAML): per-video → matrix over inputs.recordings, max-parallel 2. per-scene → matrix over the director's scenes, max-parallel 3, fail-fast false. The gate is max-parallel. Fan-in: needs.per-video.outputs.words[matrix.scene.sourceIndex] — each scene reaches back to its own source video's transcript by index.

A pipeline step is a proxy rule

.bffless/proxy-rules/workflow-studio/rules/scenes/post/

SCREEN: open rules/scenes/post — rule.yaml plus prep.fn.js, parse.fn.js, collect, sweep, each with a .fn.test.yaml beside it. prep shapes the request, the model does the thinking, parse turns the answer into typed outputs the next step can use. No server to deploy — it's a BFFless rule set.

An island is a person in the loop

uses: island — islands/cut-editor. The run stops, the harness mounts a real React UI in the page, you trim the scene, and the island's outputs (keep spans) flow into the next step. Same for the blog editor. form steps are the lightweight version: the cover job asks for cover direction with a declared form.

A workflow is a folder

SCREEN: github.com/bffless/workflow-implementations → workflows/workflow-studio. .bffless/workflows (the YAML), .bffless/proxy-rules (pipeline steps), islands/ (UIs), scripts/ (TS steps), tests beside every piece. CI runs publish-workflow, which pushes the rules and uploads the bundle to the project.
